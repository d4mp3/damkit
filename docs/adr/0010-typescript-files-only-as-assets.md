# ADR-0010: No TypeScript agents. TS/CSS files in the repo only as skill assets.

- Status: Accepted; the sentence about flags in `typescript-conventions` superseded by [ADR-0014](0014-knowledge-skills-hold-only-what-the-model-lacks.md)
- Date: 2026-09-29

## Context

After adding frontend, the question came up whether the repo should get "TypeScript" elements:
a `typescript-expert`-style agent, templates for `tsconfig.json`/`eslint.config.js`/test setup,
a frontend project starter, or rewriting the hook in TS/Node.

## Decision

- **No per-language or per-framework agents**, same as with `django-expert` (ADR-0002).
  TS/React knowledge is in skills, and the review perspective in `frontend-reviewer` (ADR-0007).
- **A file goes into the repo only as a skill asset** (`skills/<name>/assets/`) and only when
  a concrete file carries decisions better than prose and cannot be generated by a tool.
  Currently there is one: `building-ui/assets/tokens.css` (layer structure and checked contrast).
- **No `tsconfig`/ESLint/Vitest templates and no project starter.** Scaffolders
  (`pnpm create vite`, `shadcn init`, `playwright init`) generate them in the current version, and the
  `typescript-conventions` skill lists the flags and rules to add.
- **The hook stays in Python**: one runtime, and one I have on every machine.

## Alternatives considered

- **`templates/frontend/` with configs**: they age faster than tool versions and duplicate
  scaffolders. The model would have to check whether they are up to date anyway.
- **Hook in TypeScript**: would require Node and a build, or `tsx`, on every machine. It would gain nothing.

## Consequences

- A new asset needs a justification: what decision it carries and why it cannot be generated.
- If the model's recurring mistakes in TS configuration prove persistent, we return to
  templates with a new ADR that supersedes this one.
